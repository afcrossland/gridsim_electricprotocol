# Electric Futures infrastructure

Terraform for hosting this site on GCP, in the same project as gridsim
(`project-08077ad6-f39e-4a3c-b19`). It shares gridsim-deploy's state bucket
(`gridsim-tf-state`) under its own prefix, `electricfutures/<env>`, so the two never touch each
other's state. gridsim's own resources, including the backend the `/klute` gate proxies to,
stay in gridsim-deploy. They are passed in here as plain values in `terraform.tfvars`.

`modules/electricfutures` sets up one environment:

- the Firebase Hosting site `electricfutures-<env>`, plus a Firebase web app whose config the
  gate's sign-in page uses;
- the `/klute` sign-in gate on Cloud Run, `klute-gate-<env>`, with its own service account, an
  Artifact Registry repo `electricfutures-repo-<env>`, and a session-signing key (generated by
  `random_password`, so it sits in state like gridsim-deploy's DB password). The gate's image is
  deployed by `.github/workflows/deploy.yml`, and Terraform ignores it;
- keyless GitHub Actions deploys through Workload Identity Federation: pool `github-ef-<env>`
  accepts tokens only from this repo's `Development` (dev) or `main` (prod) branch, and service
  account `ef-deploy-<env>` does the deploying. Firebase Hosting roles can't be scoped to one
  site, so this account could also deploy the gridsim-frontend sites.

## One-time setup, in order

1. **Firebase Auth** (project-wide, not in Terraform): Firebase console → Authentication →
   Sign-in method → enable **Google**. Then Settings → Authorized domains → add
   `electricfutures-dev.web.app` and `electricfutures-prod.web.app` (and any custom domain).
2. **Allowlist:** fill `klute_allowed_emails` in `environments/<env>/terraform.tfvars`. Empty
   means nobody can get in.
3. **Apply** with gcloud application-default credentials. Do dev first, then prod
   (prod is confirm-first, as in gridsim-deploy):

   ```bash
   cd infra/terraform/environments/dev && terraform init && terraform apply
   ```

   The gate starts on a placeholder image until the first deploy.
4. **MapTiler:** add the environment's `web.app` domain to the allowed origins of the key in
   `deploy.yml` (gridsim-frontend's). The next push to that environment's branch deploys. GitHub needs no
   settings: `.github/workflows/deploy.yml` builds the pool and service account names from
   the same fixed names this module uses, so renaming either here means changing it there.
   Making `Development` the default branch (repo admin) is optional but saves picking it as
   the base of every PR and lets spreadsheets uploaded on the website reach the import.

Adding or removing someone from /klute means changing `klute_allowed_emails` and running
`terraform apply`.

Both environments' backends have a klute password (gridsim-deploy's `enable_klute_password`;
prod since 2026-10-28), and `klute_backend_password_secret_id` points the gate at it. To rotate
it, add a new version of `gridsim-backend-<env>-klute-password` and deploy a new revision of both
the backend and the gate: both read it as an environment variable when an instance starts, so
running instances keep the old value.

## Policy database

`modules/electricfutures/database.tf` creates the Policy Explorer's database (ROADMAP.md,
decision 1) on this environment's **existing gridsim Cloud SQL instance**
(`cloudsql_instance_name`: `gridsim-dev-db` / `gridsim-prod-db`). gridsim-deploy owns the
instance; this only looks it up and adds to it:

- database `electricfutures`, which Terraform will never drop (`deletion_policy = "ABANDON"`
  and `prevent_destroy`);
- login `electricfutures`, with a generated password (it sits in Terraform state, like the
  gate's session key);
- secret `electricfutures-<env>-database-url`, holding the whole `DATABASE_URL` that
  `klute/gate/ep_db` reads, in Cloud SQL socket form
  (`postgresql+psycopg://electricfutures:…@/electricfutures?host=/cloudsql/<connection name>`);
- `roles/cloudsql.client` and access to that secret for the gate's service account, whose
  Cloud Run service mounts the instance at `/cloudsql` and gets the secret as `DATABASE_URL`, to
  serve `/api/policy/data` (Firebase Hosting rewrites `/api/policy/**` to it).

The spreadsheet import (`.github/workflows/import-input.yml`, Development only) keeps the dev
database in step with `src/data` as service account `ef-import-<env>`: the same
`github-ef-<env>` pool as deploys, but only the database secret and `roles/cloudsql.client`.
It doesn't run migrations - do those by hand as below before merging a schema change.

The tables come from Alembic, not Terraform. After applying, from `klute/gate/` with the
[Cloud SQL Auth Proxy](https://cloud.google.com/sql/docs/postgres/sql-proxy) running as
`cloud-sql-proxy --unix-socket /cloudsql <connection name>` (the `cloudsql_connection_name` output),
so the secret's URL works unchanged:

```bash
export DATABASE_URL="$(gcloud secrets versions access latest --secret electricfutures-dev-database-url)"
alembic upgrade head
python -m ep_db.import_json
python -m ep_db.import_json --check
```

This is a write to the shared gridsim instance, so dev first and prod confirm-first.

**Cloud SQL permissions caveat.** Cloud SQL makes every user created through its API (this one,
and `gridsim_user`) a member of `cloudsqlsuperuser`, and Postgres lets `PUBLIC` connect to every
database by default. Neither user can read the other's tables unless they're granted to
`PUBLIC`, but each can connect to the other's database. To close that, the instance owner can run,
as `postgres`:

```sql
REVOKE CONNECT ON DATABASE electricfutures FROM PUBLIC;
GRANT CONNECT ON DATABASE electricfutures TO electricfutures;
-- and the same for gridsim's databases (gridsim, devdb) and gridsim_user - check nothing
-- else connects to them first.
```

That isn't done by Terraform: it changes gridsim's databases, which this repo doesn't own.
